# Telegram-алерты о выпуске npm-пакетов: дизайн

Источник требований — задача [frontend-packages#6](https://github.com/Cringe-Driven-Development-Team/frontend-packages/issues/6) (`gh issue view 6 -R Cringe-Driven-Development-Team/frontend-packages`). Там заданы формат карточки, статусы, кнопки и критерии приёмки; документ их не повторяет, а фиксирует, как это устроено, решения, принятые при обсуждении, и проверенные факты. Если документ и задача расходятся, прав документ. Решения, которые я принял сам, помечены «(моё решение)».

## Зачем

После выпуска команда (в основном фронтендеры и куратор) получает в треде **Frontend / Releases** одну карточку на выпуск. Её читают для общего понимания: что вышло, какие версии, нужна ли миграция, всё ли прошло. Решения по ней принимаются позже, при планировании, поэтому достоверность и краткость важнее скорости, а кнопки ведут к подробностям и ничего не запускают.

## Исходное состояние (проверено)

- `.github/workflows/release.yml`: job `release-please` (выходы `releases_created`, `paths_released`) и job `publish` (`if: releases_created == 'true'`, `id-token: write`): checkout → setup-bun → `bun install --frozen-lockfile` → `bun run build` → `bun run verify:packages` → setup-node 22.14.0 → `npm install -g npm@^11.5.1` → проверка версий → `bun scripts/publish-released.ts "$PATHS_RELEASED"`.
- `scripts/publish-released.ts`: `orderForPublish` (React, затем Zustand, затем остальные в исходном порядке), `publishReleased(paths, run, isPublished)` пропускает уже опубликованные версии (`npm view name@version version`) и бросает ошибку на первом ненулевом коде `npm publish`. Тесты — `scripts/publish-released.test.ts`.
- Секреты: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — секреты организации, доступные репозиторию; `TELEGRAM_RELEASES_TOPIC_ID` — секрет репозитория. Проверено через `gh api repos/…/actions/organization-secrets` и `gh secret list`.
- Теги вида `<component>-v<version>` (`react-v1.3.0`, `zustand-v1.0.2`, `openapi-v0.2.1`, `oxlint-plugin-jsdoc-v0.1.2`), `include-component-in-tag: true`. Тело GitHub Release совпадает с секцией версии в `CHANGELOG.md`.
- Секции changelog: `Features`, `Bug Fixes`, `Dependencies` (зависимый выпуск: «The following workspace dependencies were updated … @cdd-team/react bumped from ^1.2.1 to ^1.3.0»); release-please добавляет `⚠ BREAKING CHANGES` для ломающих коммитов.
- `bump-minor-pre-major: true`: в `0.x` ломающее изменение поднимает minor, а не major. Поэтому breaking определяется по секции changelog, а не по номеру версии.
- `bun run test:integration` проверяет React + Zustand (happy-dom) и vanilla Zustand. Для OpenAPI и плагина jsdoc интеграционных проверок нет.

## Цели

Всё из раздела «Что сделать» и «Приёмка» задачи, в том числе:

- ровно одна карточка на выпуск, в том числе при ошибке до публикации;
- версии, тип изменения, краткое описание, причина зависимого выпуска, блок миграции, блок совместимости только по реальной проверке;
- статусы ✅ / ⚠️ / ❌ по фактическому результату, подтверждение версии в registry с повторами;
- различие «опубликован сейчас» и «уже был, пропущен» при повторном запуске; нет алерта, если всё пропущено без ошибок;
- сбой Telegram виден в логах и summary отдельно от результата выпуска;
- тесты с подменёнными npm/Telegram, обновлённый runbook, примеры карточек к PR.

## Не цели

Из задачи: уведомления о деплое, PR и ревью; изменения в других репозиториях и в общих workflow `.github`; перенастройка release-please, npm-авторизации, регистрация пакетов; кнопки запуска или повторной публикации; генерация описаний через LLM.

Дополнительно (моё решение): сбой самого шага release-please карточки не даёт. Если action упал, неизвестно, созданы ли релизы, а `paths_released` недоступен. Такой сбой виден как обычный красный workflow.

## Анти-цели (провал, даже если работает)

- Карточка утверждает то, чего не было: «опубликован» без подтверждения registry, «отсутствует» вместо «не подтверждена», выдуманная причина сбоя, способ миграции или совместимость без проверки.
- Пропущенная версия выдана за новую публикацию; повторный «успех» при перезапуске, где ничего не опубликовано.
- Отдельные сообщения по пакетам; алерт на release PR или на запуск без релизов.
- Токен бота или технический лог в чате; Telegram-секреты в job с `id-token: write`.
- Сбой Telegram роняет или искажает результат публикации.
- Код завязан на фиксированный список из четырёх пакетов.

## Устройство

Решение пользователя: собственные Bun-скрипты в `scripts/` на `fetch` к Telegram Bot API, без сторонних actions; `publish-released.ts` пишет результаты в JSON; в конце workflow шаг собирает карточку и отправляет её. Тесты на `bun test` с подменёнными npm и Telegram.

### Workflow

**Job `publish`** (тот же, что сейчас, плюс):

- У каждого шага есть `id`. Новый шаг `bun run test:integration` (id `integration`) идёт после `verify:packages` и до setup-node. Упавшие интеграционные тесты — ошибка до публикации, публикация не начинается (моё решение: совместимость показывается только по проверке на релизном коммите, поэтому проверка нужна в том же запуске).
- Шаг публикации запускается как `bun scripts/publish-released.ts "$PATHS_RELEASED" --report release-report.json`.
- Шаг `actions/upload-artifact` с `if: always()` загружает `release-report.json` (`if-no-files-found: ignore`).
- В `outputs` job экспортирует `outcome` ключевых шагов: `install`, `build`, `verify`, `integration`, `node` (setup-node + npm + проверка версий, одним значением: первый не-`success` среди них), `publish`.

**Новый job `notify`** (моё решение: отдельный job, чтобы Telegram-секреты не попадали в job с `id-token: write`):

- `needs: [release-please, publish]`, `if: always() && needs.release-please.outputs.releases_created == 'true'`. Release PR и запуск без релизов дают `releases_created != 'true'`, алерта нет.
- `permissions: contents: read, pull-requests: read`.
- checkout релизного коммита с `fetch-depth: 0` (нужны теги), setup-bun, `bun install --frozen-lockfile`, `actions/download-artifact` (отсутствие артефакта допустимо), затем `bun scripts/release-notify.ts`.
- Через env получает: `PATHS_RELEASED`, `outputs` шагов publish, `needs.publish.result`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_SHA`, `GH_TOKEN: ${{ github.token }}`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_RELEASES_TOPIC_ID` (все три из `secrets.*`).

### `publish-released.ts`: отчёт

Порядок публикации и остановка на первой ошибке сохраняются. Для каждого пути из `orderForPublish(paths)` в отчёт пишется запись:

```ts
type PackageResult = {
	path: string;          // "packages/zustand"
	name: string;          // "@cdd-team/zustand"
	version: string;       // из package.json релизного коммита
	status: "published" | "skipped" | "unconfirmed" | "failed" | "not-attempted";
	reason?: string;       // для failed: краткая достоверная причина
	errorKind?: "auth" | "conflict" | "network" | "unknown";
};
```

- `skipped` — версия уже была в npm до попытки (существующая проверка `isPublished`).
- `published` — `npm publish` вернул 0 и точная версия видна через `npm view name@version version`. Проверка с ограниченными повторами (моё решение: до 6 попыток с паузой 10 с; интервалы и функция ожидания инжектируются для тестов).
- `unconfirmed` — `npm publish` вернул 0, но за все повторы версия не появилась. Это не ошибка публикации: следующие пакеты публикуются (моё решение), но процесс завершается с кодом 1, чтобы запуск был заметен.
- `failed` — ненулевой код `npm publish`. Следующие пути получают `not-attempted`, процесс завершается с кодом 1.
- Вывод `npm publish` по-прежнему идёт в лог job; stderr дополнительно буферизуется для классификации: `E401`/`E403`/`ENEEDAUTH`/`OIDC` → `auth` («npm отклонил авторизацию»), `E409`/`EPUBLISHCONFLICT`/«cannot publish over» → `conflict`, `ETIMEDOUT`/`ECONNRESET`/`ENOTFOUND`/`EAI_AGAIN` → `network`, иначе `unknown` с причиной «npm publish завершилась кодом N». Текст stderr в отчёт и в карточку не попадает.
- Отчёт пишется и при ошибке (в `finally`). Без `--report` скрипт ведёт себя как сейчас (для ручного восстановления из runbook).

### `release-notify.ts`: сбор и отправка

Разбит на чистые функции (сбор модели, рендер, нарезка кнопок) и тонкий слой ввода-вывода (`git`, `gh api`, `fetch`), который подменяется в тестах. Имя файла и разбиение по модулям — на усмотрение исполнителя.

**Источники данных по каждому пути из `PATHS_RELEASED`:**

| Поле | Источник |
| --- | --- |
| npm-имя, целевая версия | `package.json` пути в релизном коммите (checkout `GITHUB_SHA`) |
| компонент | `release-please-config.json` → `packages[path].component` |
| предыдущая версия | максимальная по semver среди тегов `<component>-v*`, меньшая целевой; нет такой — «первый выпуск». npm `latest` не используется |
| тип изменения | semver-разница предыдущей и целевой: `major`/`minor`/`patch`; для первого выпуска не выводится |
| описание, breaking | секция `## [<версия>]` в `CHANGELOG.md` пути |
| ссылка на GitHub Release | `<server>/<repo>/releases/tag/<component>-v<version>` |
| результат | `release-report.json`; записи нет → см. «Статус» |

Ссылка «Изменения»: release PR, влитый этим коммитом (`gh api repos/{repo}/commits/{sha}/pulls`, первый merged PR). Не нашёлся — ссылка на GitHub Release первого пакета (моё решение). «Проверки» и «Логи ошибки»: `<server>/<repo>/actions/runs/<run_id>/attempts/<attempt>`. «Восстановление выпуска»: раздел 5 runbook на GitHub по `GITHUB_SHA`.

**Описание из changelog.** Пункты из `Features` и `Bug Fixes` без хвоста `([sha](url))`, по одному на строку; длинный текст сокращается. Если секция содержит только `Dependencies`, пишется причина зависимого выпуска из фактов: «Обновлён диапазон `@cdd-team/react` до `^1.3.0`» (peer и dev одинаковые; если различаются — по peer). Если секцию разобрать не удалось или в ней нет пунктов — «Подробности в changelog» со ссылкой на GitHub Release, без резюме.

**Breaking.** Есть секция `⚠ BREAKING CHANGES` — пакет помечается, в карточке блок **«⚠️ Требуется миграция»**: пункты секции (сокращённые) и ссылка на GitHub Release. Инструкцию по миграции не формулируем; если в пунктах её нет, пишем «Изучите breaking changes по ссылке». Major без этой секции миграцию не включает; minor в `0.x` с этой секцией — включает.

**Совместимость.** Блок есть, если `integration == 'success'` и среди выпущенных есть React или Zustand, причём хотя бы один из них в итоге доступен (`published`/`skipped`). Текст: «Интеграционные проверки React `<v>` + Zustand `<v>` прошли», версии — из `package.json` обоих пакетов в релизном коммите (именно они проверялись). Для остальных пакетов блока нет.

**Статус карточки:**

- Публикация не началась (любой шаг до `publish` не `success`, отчёта нет): **«❌ Выпуск не состоялся»**, этап — первый не-`success` шаг по-русски («установка зависимостей», «сборка», «проверка архивов», «интеграционные проверки», «подготовка Node/npm»), причина — «шаг завершился с ошибкой, подробности в логах». Все пакеты перечислены как неопубликованные с целевыми версиями. Действие: «исправить причину и перезапустить job publish».
- Отчёт есть, все записи `skipped`, ошибок нет — **алерт не отправляется**, в summary пишется, почему.
- Есть `failed`/`unconfirmed`/`not-attempted` и хотя бы один `published` или `skipped` — **«⚠️ Выпуск завершён частично»**; если ничего не доступно — **«❌ Выпуск не состоялся»**.
- Иначе (всё `published`, часть может быть `skipped`) — **«✅ Библиотеки опубликованы»**.
- Отчёта нет, а шаг `publish` упал или отменён, либо outcomes шагов пустые (job отменён или runner умер, GitHub не экспортировал `outputs`): этап определить нельзя. Заголовок **«⚠️ Результат выпуска неизвестен»**, пакеты описываются по проверке registry (ниже), действие — «проверить registry и логи, при необходимости перезапустить job» (моё решение).

**Проверка registry без отчёта** (моё решение). Если отчёта нет, `notify` сам проверяет каждую версию через `npm view <имя>@<версия> version`: только чтение, без секретов, одна попытка на пакет. Так карточка ошибки до публикации на повторном запуске не скажет «не опубликован» о версии, ушедшей в первой попытке. Версия видна — «доступен в npm» (с npm-кнопкой). Не видна — «в registry не видна». Проверка не удалась — «состояние в npm не проверено». Ни в одном случае не пишем «отсутствует». Если при ошибке до публикации все версии уже доступны, карточка всё равно отправляется (в запуске была ошибка), с заголовком «❌ Выпуск не состоялся» и пометкой, что все версии уже были в npm.

Подзаголовок: «frontend-packages · N пакетов» при успехе, «опубликовано K из N» при частичном. Для ошибки: этап, пакет/версия, причина (из `errorKind`), какие пакеты доступны, какие нет, и действие по виду ошибки: `auth` — «проверить Trusted Publisher для <пакет> и перезапустить job»; `conflict` — «версия уже занята, проверьте registry»; `network`/`unknown` — «посмотреть логи и перезапустить job». `unconfirmed` — «Публикация не подтверждена, проверьте `npm view <имя>@<версия>`»; не «отсутствует».

Значки пакетов: ✅ опубликован сейчас, ↩️ уже был в npm (пропущен), ⏳ не подтверждён, ❌ ошибка, ⏸ не публиковался. Конкретные значки — на усмотрение исполнителя, если различия видны.

**Оформление.** Telegram `parse_mode: "HTML"` (моё решение: экранируются только `&`, `<`, `>`). Имена и версии — в `<code>`, имя пакета ссылкой на его GitHub Release. Блоки разделены пустой строкой, открытых URL в тексте нет, `link_preview_options: { is_disabled: true }`. Описания сокращаются так, чтобы сообщение уложилось в 4096 символов видимого текста: сначала пункты changelog (с «…и ещё N» и ссылкой на Release), версии и статусы всех пакетов не сокращаются никогда.

**Кнопки** (`reply_markup.inline_keyboard`, только `url`):

- Успех: по два в ряд — `<имя без scope> <версия> в npm` → `https://www.npmjs.com/package/<name>/v/<version>` для каждого доступного пакета; затем ряд `[Изменения] [Проверки]`.
- Частичный сбой / ошибка: ряд `[Логи ошибки] [Восстановление выпуска]`, затем npm-кнопки доступных версий.
- Пропущенные пакеты тоже получают npm-кнопку (версия доступна). Неподтверждённые и неопубликованные — нет.

**Отправка и сбой Telegram.** `POST https://api.telegram.org/bot<token>/sendMessage` с `chat_id`, `message_thread_id` (из `TELEGRAM_RELEASES_TOPIC_ID`), `text`, `parse_mode`, `link_preview_options`, `reply_markup`. До трёх попыток на сетевую ошибку или 5xx/429 (с учётом `retry_after`). Текст карточки всегда пишется в `$GITHUB_STEP_SUMMARY` (без кнопок-секретов: URL кнопок секретов не содержат). Если отправка не удалась: в лог и summary — «Telegram: сообщение не доставлено (<код и description ответа>)», токен не печатается, job `notify` завершается с кодом 1. Job `publish` и его результат от этого не меняются. Нет секретов Telegram — та же ошибка доставки, карточка остаётся в summary.

### Повторный запуск

«Re-run failed jobs» перезапускает `publish` и `notify` с теми же выходами release-please. Уже доступные версии получают `skipped` и в карточке показаны как «уже был доступен, пропущен». Если в перезапуске всё `skipped` и ошибок нет, нового алерта нет: успех уже сообщён или оператор восстановил вручную.

## Тесты

Всё на `bun test`, без сети и без реального registry/чата. Файлы в `scripts/*.test.ts`, чтобы их подхватил `test:scripts`.

- `publish-released`: существующие тесты остаются; новые — отчёт для успеха, `skipped`, `failed` с остановкой и `not-attempted`, задержка registry (версия видна с N-й попытки), `unconfirmed` после всех повторов, классификация stderr, отчёт пишется при ошибке.
- `release-notify`, сценарии из приёмки на подменённых данных: полный успех (React+Zustand и один OpenAPI), зависимый Zustand с объяснением диапазона, breaking в `0.x` и major без breaking, первый выпуск, ошибка до публикации (сборка, интеграционные), ошибка до публикации на перезапуске, когда часть версий уже в npm, пустые outcomes без отчёта, ошибка первого пакета, частичный сбой, задержка registry, неподтверждённый результат, всё пропущено (нет отправки), перезапуск с `skipped` + `published`, недоступность Telegram (5xx, сетевая ошибка, нет секретов), экранирование `<`/`&` в changelog, длинный changelog в пределах 4096, раскладка кнопок для 1–5 пакетов, неизвестный новый пакет без правок кода.
- Скрипт-генератор (или тест со снимком) печатает примеры карточек успеха и частичного сбоя; их текст прикладывается к PR.

## Документация
